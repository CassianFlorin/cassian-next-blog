## 📖 How It All Happened

A self-hosted service was running on a Debian 12 VPS: a Docker container with a bind-mounted data volume, with a SQLite database at its core. While cleaning up the disk, a directory that “appeared to be a remnant of an older version” was completely `rm -rf`ed.

The problem is: **That's not the directory from the old version; it's the data volume of a running container.**

To make matters worse, besides the database, there are two other things sitting in this directory:

- Daily backup script (create a tar archive → GPG AES256 symmetric encryption → upload to cloud storage)
- **GPG backup password file—the only copy in the entire universe**

The encrypted backups from the last 5 days are sitting quietly on the cloud storage, but I can't decrypt a single one:

## 🧊 Golden Rule: Secure the Scene First

Your first reaction upon realizing you’ve accidentally deleted something shouldn’t be “fix it right away,” but rather **to stop any urge to write to the disk**:

- **Do not restart the container/service**. The process may still be holding handles to the deleted files; restarting it will result in their permanent loss. Even if the handles are gone, the process will continue to run using its in-memory configuration, giving you time to troubleshoot;
- **Minimize writes to the target disk**. The data blocks of the deleted files are still in the free block pool, and every write to the disk could overwrite them;
- **Always write the output of the recovery operation to a different disk**.

Next, we took four different routes in order of cost (from lowest to highest) and time window (from shortest to longest).

## ❌ Approach 1: Retrieve from the process handle (5 minutes, unsuccessful)

On Linux, when a file is deleted but is still open by a process, the data is actually still there and can be copied back exactly as it was from `/proc`:

```bash
# 找被删但仍被打开的文件
ls -l /proc/<pid>/fd/ | grep -i deleted

# 找到的话直接复制回来
cp /proc/<pid>/fd/<N> /安全位置/recovered.db
```

This is the path with the lowest cost and the highest success rate—**always be the first to try it**.

Unfortunately, it didn't work this time: the service's SQLite connection is enabled on demand, and the process does not hold the file handle for an extended period.

## ❌ Option 2: ext4 Log Recovery (30 minutes, unsuccessful)

The ext4 journal temporarily retains the metadata of deleted inodes; `ext4magic` can use this to restore the complete directory tree:

```bash
apt-get install -y ext4magic

ext4magic /dev/vdb1 \
  -a "$(date -d '今天 03:00' +%s)" \
  -b "$(date -d '删除前一刻' +%s)" \
  -f "相对挂载点的路径" \
  -r -d /另一块盘/recover
```

I ran into three pitfalls, all of which are worth noting:

1. **`-b` must use the timestamp before deletion**. Using the timestamp after deletion will result in `Inode not found`—the directory inode has already been released, so resolving the path based on "now" will naturally fail;
2. **Beware of false leads**.The `Inode found ... is allocated` in the output looks like “the directory was actually moved with `mv`,” but checking with `find /挂载点 -inum <号>` reveals that it’s the **parent directory’s** inode—the tool only parsed up to the parent level;
3. `-m`’s full-scan “magic” mode directly causes a segmentation fault (an old bug in version 0.3.2); don’t count on it as a last resort.

The final conclusion is `No undeled inode in journal found`: The data was deleted more than 3 hours ago, and other services on the same disk are still writing to it, so **the journal has long since been overwritten**. On a busy disk, the time window for log recovery may be only a few minutes—if you’re going to take this route, you’ll have to act fast.

## ✅ Option 3: photorec free-block carving (20 minutes, successful)

File carving does not rely on any file system metadata; instead, it extracts the entire file directly from free blocks on the disk based on the **file header signature**. SQLite is an ideal target:

- Fixed file header (`SQLite format 3\0`) and strong signature;
- Small single-file size (tens to hundreds of KB), likely stored contiguously and resistant to fragmentation;
- The database is repeatedly written to disk, and free blocks often contain **an entire time series of historical versions**.

```bash
apt-get install -y testdisk sqlite3

photorec /log /d /另一块盘/carve /cmd /dev/vdb1 \
  partition_none,options,freespace,fileopt,everything,disable,sqlite,enable,search
```

Parameter Breakdown:

- `options,freespace`— Only scan **free blocks**; do not touch in-use data, which makes the process much faster;
- `fileopt,everything,disable,sqlite,enable`— Disable everything first, then enable the SQLite signature individually to avoid carving out a bunch of irrelevant files;
- The output directory is on a separate drive.

It took just a few minutes to scan the 107GB partition, revealing **42 SQLite files**.

## 🔍 Candidate Identification: Finding the "Moment of Deletion" Among 42 Afterimages

What’s been carved out isn’t “a single answer,” but rather dozens of historical snapshots left behind by the database as it repeatedly settled over the past few months. Which one is the most recent?

**Step 1: Batch Inspection**—First, eliminate the damaged ones:

```bash
for f in carve-hits/*.db; do
  ok=$(sqlite3 "$f" "pragma integrity_check;" | head -1)
  # 再抽几个业务表的行数和关键字段
done
```

**Step 2: Identify monotonic quantities in the business data**. The files themselves do not have reliable timestamps (the mtime values of the fabricated files all correspond to the time they were created), but the business data contains a natural clock:

- Cumulative traffic counter—monotonically increases within the same billing cycle;
- Number of records—increases but never decreases for each user or order;
- Expiration date field—renewal simply pushes the date forward.

**Step 3: Find an external temporal anchor**. A status file from a scheduled task on the server—which records which users received expiration reminders on a given day—was spared from accidental deletion. The expiration dates it records match exactly with the fields in the candidate database, allowing us to pin the candidates to the timeline.

Three chains of evidence intersect, pinpointing the sole candidate that includes both the “most recent renewal” and the “most recent new user.” `integrity_check` returns “ok”; all configuration tables are complete, and the key settings match those of the live environment. **This is the final version from the time of deletion (or very close to it).**

  <strong>

  —Cumulative traffic, the number of rows that only increases, and expiration

## 🚀 Deployment and Validation

```bash
mkdir -p /数据卷路径/db
cp candidate-9.db /数据卷路径/db/app.db && chmod 600 /数据卷路径/db/app.db
docker restart <容器>
```

When verifying, don’t just check that “the container is up”: ensure there are no database errors in the logs, that the web service returns a 200 status code, that the external domain is reachable, and that all core business functions have been tested one by one. If everything passes, there will be **zero configuration loss**; the worst-case scenario is simply a slight loss of statistical data from the very last segment before deletion.

## 🛡️ Aftermath: Don't Let the Accident Happen Again

1. **The backup chain was rebuilt on the same day**:flock anti-re-entry → Stop containers to ensure SQLite consistency → tar → GPG AES256 → rclone upload → Remote verification → Local/remote retention policy, and manually test the entire workflow once—a backup script that isn’t tested is as good as not written;
2. **I immediately saved a second copy of the new password in my password manager**—the most painful part of this incident wasn’t deleting the database; it was that “all the backups were there, but there was only one key, and it was locked in the same drawer as the database”;
3. Keep temporary files generated during the recovery process for a few days to monitor them; clean them up only after confirming there are no issues.

## 🧭 Quick Reference Chart for Recovery Routes

| Order | Route                              | Time Window                                 | Applicable Scenarios                                   |
| ----- | ---------------------------------- | ------------------------------------------- | ------------------------------------------------------ |
| 1     | `/proc/<pid>/fd` Process handle    | While the process is running                | File has been deleted but the process is still running |
| 2     | ext4 log (ext4magic)               | A few minutes to a few hours on a busy disk | Shortly after deletion, when the disk is not busy      |
| 3     | photorec idle block carving        | Before data blocks are overwritten          | Small files with strong file headers (SQLite, etc.)    |
| 4     | Old backups + manual data recovery | Always available                            | Fallback option when the first three fail              |

Try them from top to bottom: costs increase, and the time window decreases. May you never have to use the third one—but if you do, remember to secure the scene first.
