The Lenovo M1688W Pro at home is a wireless model, so whoever wants to print has to connect to it from their phone each time—and even then, it doesn’t always recognize the device.A few days ago, I wanted to solve this once and for all by setting it up as a permanent print queue on my Feiniu NAS. I figured it would take about ten minutes—just find a PPD file and upload it, and I’d be done. In reality, it took me an entire evening, and almost all the hurdles I ran into were related to the model name.

## 📄 PPD just handles the description; another program does the actual work

First, let’s clarify what a PPD is. In CUPS, each printer corresponds to a PPD file—a plain-text file that describes the printer’s paper size capabilities, resolution (in dpi), and whether it supports color printing. Since I’ve installed a Lenovo driver on my Mac, I’ll start by checking the driver library.

```bash
ls /Library/Printers/PPDs/Contents/Resources/
```

Thirty `.ppd.gz`s, with `lenovom1688dwpro.ppd.gz` inside each one. I was pretty happy, so I unzipped them and got ready to upload them directly to my NAS.

After unzipping the file, I took a quick look at the contents and got stuck on this line.

```
*cupsFilter: "application/vnd.cups-raster 50 rastertolenovo"
```

What this means is that the PPD is responsible only for describing capabilities, while the task of converting the page into a byte stream that the printer can recognize is handled by an external program called `rastertolenovo`. The PPD is a text file that can be read on any machine. The same cannot necessarily be said for that program.

```bash
file /usr/libexec/cups/filter/rastertolenovo
# Mach-O universal binary with 2 architectures [x86_64] [arm64]
```

Mach-O. When copied to Debian, it’s just a bunch of unrecognizable bytes. It wasn’t until then that I realized that having just the PPD was like moving only the instruction manual—the machine that actually does the work was still right where it was.

<Callout emoji="🔑">
  <strong>
    PPDs are cross-platform, but raster filters must match the OS architecture.
  </strong>
  If you take a PPD from another system and transfer it to CUPS on Linux, the
  job will get stuck in the queue with a "Filter failed" error.
</Callout>

## 📦 Of the three packages on the official website, only one includes W Pro

Lenovo's Linux driver page is on the [Lenovo Graphics Official Website](https://www.lenovoimage.com/index.php/services/servers_drivers?cat_id=2&OS=Linux). There are three packages related to 1688; none of their names include a model number, so you'll need to expand the "Compatible Models" column and compare them one by one.

The comparison results are a bit counterintuitive.

| Driver Pack                              | Includes M1688W Pro | Format      | Model list ends at |
| ---------------------------------------- | ------------------- | ----------- | ------------------ |
| G Series and GM Series Kirin V10 Drivers | ✅                  | zip / 115MB | `M1688W Pro`       |
| G Series, GM Series, UOS                 | ❌                  | zip / 164MB | `M1688DW Pro`      |
| lenovo-100-m1520-m1688-series-linux      | ❌                  | 7z / 78MB   | `M1688W` (No Pro)  |

The one with the most similar name is called `lenovo-100-m1520-m1688-series-linux`. The model list includes `M1688W` and `M1688DW`, neither of which has “Pro” in the name. The third one, which includes `M1688W Pro`, is titled “G Series and GM Series Kirin V10 Drivers”—the name doesn’t even contain a single “1.” The absence of “Pro” means it’s a different set of PPDs; I only realized this after unpacking the package and checking the files—I’ll explain more on that later.

There was a little hiccup with the download link. The "`href`" part of the download icon on the page was empty, and the URL was stored in the "`data-href`" attribute, where it was dynamically generated by JavaScript. Here's what I managed to extract.

```bash
curl -L -o lenovo-kylin.zip \
  "https://lenovo-upload.oss-cn-beijing.aliyuncs.com/drivers/G262DN_Series_drivers_Lin_20240109140629.zip"
```

When extracted, there are four .deb files, organized by architecture.

```text
lenovo-printer-driver_1.51-230329_amd64.deb
lenovo-printer-driver_1.51-230329_arm64.deb
lenovo-printer-driver_1.51-230329_loongarch64.deb
lenovo-printer-driver_1.51-230329_mips64el.deb
```

Loongson and MIPS64EL are also included, since this package was originally developed for Kylin and Tongxin. Feiniu runs on x86; use the AMD64 version, which is 30.4 MB.

## 🔧 After unpacking the .deb file, only 121 KB is usable

`ar x` Strip away the deb wrapper, `tar tJf data.tar.xz` list everything, and the first thing you're looking for will appear.

```bash
ar x lenovo-printer-driver_1.51-230329_amd64.deb
tar tJf data.tar.xz | grep -iE '1688|filter'
# ./usr/share/cups/model/lenovo/lenovom1688wpro.ppd
# ./usr/lib/cups/filter/rastertolenovo.sh
```

`lenovom1688wpro.ppd`—that’s exactly the one I have, so I don’t have to make do with the DW version. When you compare the two files side by side, you can see that they’re categorized based on the machine’s actual capabilities.The DW version is v1.14, which includes `*OpenUI *Duplex/2-Sided Printing`; the W Pro version is v1.51, and `grep -c Duplex` is listed as 0. In terms of hardware, the DW supports automatic duplex printing, while the W does not; the PPD follows the hardware configuration. You can still print using the DW version, though the interface will display an extra duplex toggle that doesn’t actually do anything.

Now let's take a look at what's actually inside this package. It's 30.4 MB, which expands to 102 MB; 31 MB of that is crammed into `/opt/lenovo/vop`—a complete set of Qt5 libraries intended for graphical user interfaces on desktop systems. Since there's no X on the NAS, this part is completely unnecessary.

Only three files are used in the print chain.

```text
/usr/share/cups/model/lenovo/lenovom1688wpro.ppd   8.7 KB
/usr/lib/cups/filter/rastertolenovo.sh              110 B
/opt/lenovo/printer/rastertolenovo                  112 KB
```

That `.sh`—the entire text is three lines long.

```sh
#!/bin/sh
LD_LIBRARY_PATH=/opt/lenovo/printer
export LD_LIBRARY_PATH
/opt/lenovo/printer/rastertolenovo "$@"
```

The one doing the work is that last 112 KB ELF file. I originally thought it would load a bunch of private .so files, but after taking a look at the `.dynamic` section, there were only five entries in the NEEDED list.

```text
libcupsimage.so.2  libcups.so.2  libpthread.so.0  libm.so.6  libc.so.6
```

They're all system libraries. Once CUPS is installed, they're all there—not a single vendor-specific dependency. This outcome is much better than I expected. `libcupsimage2` On Debian, if it's not installed alongside CUPS, it really does report that the libraries can't be found—`apt install libcupsimage2`.

There was one other thing I’d been worried about beforehand. This NAS runs a Celeron J1900, which doesn’t support AVX2. When I installed mihomo previously, the standard amd64 version crashed on startup, so I had to switch to the “compatible” version. This time, I made a point of checking the compilation targets.

```text
ELF 64-bit LSB executable, x86-64, for GNU/Linux 2.6.32, stripped
```

Compiled in 2023, targeting version 2.6.32, with x86-64 as the baseline. The old-school approach came in handy this time.

## ⬆️ Make sure you use the correct entry point during installation

In Feiniu's settings, there's an option called "Upload Driver." Just drag and drop the amd64 .deb file right into it. Once the driver is uploaded, "`Lenovo M1688W Pro`" appears in the driver list. I added it to the queue, printed a test page, and the paper came out.

<Callout emoji="⚠️">
  The CUPS-built-in 631 web interface also supports uploads, but it only accepts
  a single <code>.ppd</code> file; deb files cannot be uploaded. The Feiniu
  interface accepts driver packages. The two interfaces look similar, but they
  require different files.
</Callout>

If you want to skip those 31 MB of unnecessary Qt libraries, just package the three files in their original paths; they'll still work when extracted to the root directory.

```bash
sudo tar xzf m1688wpro.tar.gz -C /
sudo systemctl restart cups
lpinfo -m | grep -i 1688
```

There's also a line in the package that says `Conflicts: zx-printer-driver, lenovo-cups-driver`. If you've previously tried installing other Lenovo or Zhixiang drivers on the same machine, dpkg will reject them outright; you'll need to clean up the system first.

```bash
dpkg -l | grep -iE 'lenovo|zx-printer'
```

Here’s a side note. The maintainer listed in the .deb file is `Githon Technology Co., Ltd.`, while the PPD directory contains `lenovo*.ppd` and `zx_*.ppd` mixed together, and `Conflicts` also points to Zhixiang. It appears that this batch of printers and Zhixiang come from the same OEM, so a single driver package covers both brands.

## 🧭 Looking Back

Domestic printer drivers are less closed-source than I expected. When you unpack the DEB package, you find an 8.7 KB text PPD file and an 112 KB converter; the dependencies are clean, and the paths are neatly organized under `/usr/lib/cups/filter` and `/usr/share/cups/model`—it’s entirely in line with the standard CUPS setup.

The hard part was finding them. The names of the three packages were very similar, the model list wasn't visible until I expanded it, and the download links were hidden in the properties. I spent almost the entire night on this instead of actually installing them.

Once the queue was set up, I went ahead and shared it, so there was no need to install the Lenovo drivers on the Mac anymore.

```bash
sudo cupsctl --share-printers --remote-any
sudo lpadmin -p M1688WPro -o printer-is-shared=true
```

CUPS broadcasts via IPP Everywhere, so Mac's "Add Printer" feature can detect it directly. Select the default AirPrint driver, and let the NAS handle the rasterization. For troubleshooting, see `/var/log/cups/error_log`.

If your printer supports AirPrint natively, you can actually skip this entire article. All it takes is a single command—no need to mess with PPDs or filters.

```bash
lpadmin -p 打印机名 -E -v ipp://打印机IP/ipp/print -m everywhere
```

You must use the manufacturer's filter only when the printer is connected to the NAS via USB and you need the NAS to act as a network printer.
