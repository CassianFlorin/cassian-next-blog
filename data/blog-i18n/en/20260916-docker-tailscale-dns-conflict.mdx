One morning, all proxy connections using the 3x-ui route were lost, and the client logs looked like this.

```log
[TCP] dial PROXY (match Match/) 127.0.0.1:56096 --> claude.ai:443
  error: blog.cassianflorin.com:443 connect error: EOF

[TCP] dial PROXY (match Match/) 127.0.0.1:55911 --> chat.openai.com:443
  error: blog.cassianflorin.com:443 connect error: EOF
```

No matter which target I try to access, the error occurs at the same point: I cannot connect to `blog.cassianflorin.com:443`, and EOF is returned. The domain name `example.com` used consistently in the commands below refers to this one.

## There's nothing wrong with the service itself

First, check if the container is still there.

```bash
docker ps -a | grep xui
# 输出：3xui_app   Up 7 hours   127.0.0.1:2053->2053/tcp
```

It's been running for 7 hours, and port forwarding is working properly. Let's check the logs again.

```bash
docker logs --tail 20 3xui_app
# 输出显示 x-ui 3.4.2 和 Xray 26.6.27 正常启动
```

Nothing out of the ordinary either. The 3x-ui side uses `externalProxy` to disguise the traffic as HTTPS traffic visiting a public website. I went over the configuration and found no issues, but when I try to connect, I just get an EOF.

Then try typing that domain name directly on the host machine.

```bash
curl -I https://example.com
# 输出：HTTP/1.1 301 Moved Permanently

openssl s_client -connect example.com:443 -servername example.com
# 输出：Verification: OK
```

Access from the host machine is completely normal, and the certificate is valid. At this point, we’ve ruled out issues at the service, configuration, and network levels. There’s only one remaining difference: all previous tests were performed on the host machine.

## Switch to a container for testing

Resolve the same domain name inside the container.

```bash
docker exec 3xui_app nslookup example.com
```

```
Server:    127.0.0.11
Address:   127.0.0.11:53

** server can't find example.com: SERVFAIL
```

It can't be resolved inside the container. The host machine can resolve it, but the container can't, so the problem is with the container's DNS.

```bash
docker exec 3xui_app cat /etc/resolv.conf
```

```
nameserver 127.0.0.11
search tailxxxxx.ts.net
options ndots:0

# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(100.100.100.100) host(fd7a:xxxx:xxxx::xx)]
# Overrides: []
```

These three lines of information, taken together, tell the whole story. The container uses Docker’s built-in resolver `127.0.0.11`, which forwards traffic to `100.100.100.100`, and the search domain is `.ts.net`. All three point to Tailscale.

## Tailscale is running, but MagicDNS is turned off

```bash
systemctl status tailscaled
# 输出：active (running)

tailscale status --json | grep -i MagicDNS
```

```json
{
  "MagicDNSSuffix": "example.ts.net",
  "MagicDNSEnabled": false
}
```

Tailscale is indeed running, and the address `100.100.100.100` has indeed been configured, but `MagicDNSEnabled` is `false`. The container is sending all DNS queries to a server that isn't working, so naturally, all public domain names return a SERVFAIL.

## Why Are Containers Affected but the Host Machine Is Fine?

Here’s how DNS works in Docker containers. Inside the container, only the built-in resolver `127.0.0.11` is recognized. When the Docker daemon starts, it reads the host machine’s `/etc/resolv.conf` and extracts `nameserver` from it to use as the forwarding target. The lookup path is: container → `127.0.0.11` → the host machine’s DNS → the public internet.

Once Tailscale is installed, it injects its own DNS address into `/etc/resolv.conf`. This happens regardless of whether MagicDNS is enabled or not; the address remains there even when the feature is disabled. Docker reads this address and passes it on to the container as-is, so the entire chain’s exit point becomes that non-functional DNS server.

The host machine narrowly escaped disaster because its `/etc/resolv.conf` typically contains more than one `nameserver`.

```
nameserver 8.8.8.8
nameserver 114.114.114.114
```

The system tries them one by one; if the first one fails, there’s a backup. Docker’s inheritance logic works differently—I haven’t looked into exactly which one it uses—but judging by the results, it doesn’t follow this “try each one in turn” behavior.

## Three Amendments to the Law

**Explicitly assign a DNS to the container**—change `docker-compose.yml`. This is the method I ended up using.

```yaml
services:
  3xui:
    # ... 其他配置
    dns:
      - 8.8.8.8
      - 114.114.114.114
    # ... 其他配置
```

How to write `docker run`.

```bash
docker run -d \
  --name 3xui_app \
  --dns 8.8.8.8 \
  --dns 114.114.114.114 \
  # ... 其他参数
  3x-ui-3xui:latest
```

**Change the Docker daemon's default DNS** by editing `/etc/docker/daemon.json`.

```json
{
  "dns": ["8.8.8.8", "114.114.114.114"]
}
```

```bash
systemctl restart docker
```

This will affect all containers on this machine that do not have DNS explicitly configured. Think carefully before proceeding.

**Make sure Tailscale's DNS is working properly** if you still rely on it to resolve internal domain names.

```bash
tailscale set --accept-dns=true
```

Next, configure the forwarding rules in the Tailscale management console to route public domain name lookups to the public DNS.

## Verification

Restart the container and check first to see if the configuration has been updated.

```bash
docker exec 3xui_app cat /etc/resolv.conf
```

```
nameserver 127.0.0.11
options ndots:0

# ExtServers: [8.8.8.8 114.114.114.114]
# Overrides: [nameservers]
```

`ExtServers` has been changed to a public DNS server, and `Overrides` now includes `nameservers`, indicating that the explicit configuration has taken effect. Resolve the DNS again.

```bash
docker exec 3xui_app nslookup google.com
```

```
Server:    127.0.0.11
Address:   127.0.0.11:53

Non-authoritative answer:
Name:   google.com
Address: 142.250.xxx.xxx
```

It's working now, and the proxy has been restored as well.

## A Few Additional Points

`127.0.0.11` is the built-in DNS that Docker runs in each custom network. It’s responsible for allowing containers to locate each other by container name, and it also forwards external domain name queries while caching them. Therefore, the `nameserver` seen inside a container is always this DNS; to see the actual upstream server, look at the `ExtServers` line.

This issue doesn't just affect proxies. Any container that needs to resolve external domain names will be affected—whether it's a client calling an external API, an email service sending messages, or a monitoring system pushing alerts to a webhook. The symptom is that connections suddenly fail, even though the service itself appears to be functioning normally.

As for why the issue happened on that particular day, I haven't been able to determine the exact cause. It could have been due to a Tailscale restart, the container re-inheriting its configuration during rebuild, or changes to the MagicDNS settings in the background—but the logs aren't detailed enough to pinpoint the cause.

You don't need to uninstall Tailscale itself. It works quite well for connecting devices within a local network; you just need to explicitly configure the container's DNS settings.

## Habits That Stick

Don't expect containers in a production environment to inherit the correct DNS; just hard-code the `dns` field—it's a one-liner.

To detect similar issues early on, you can have the health check measure the resolution at the same time.

```yaml
services:
  app:
    healthcheck:
      test: ['CMD', 'nslookup', 'google.com']
      interval: 30s
      timeout: 10s
      retries: 3
```

The part that took the most time this time was that we spent the entire hour or so at the beginning testing on the host machine. The service was running, the ports were open, the certificates were valid, and the domain was accessible—everything was working as expected. The only thing nobody thought to do was go into the container and test it again.
