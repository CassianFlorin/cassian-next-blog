# Troubleshooting Codex CLI Configuration for Relay Stations

When trying to connect to a third-party relay server with the new version of Codex CLI, you’re most likely to run into a problem here: even though you’ve entered the relay server’s address and key, the request still goes to `api.openai.com`, and then continues on to `401 Unauthorized`.

This article documents the complete process of integrating the Codex CLI (including the Codex built into the ChatGPT desktop app; tested with **v0.145.0**) with the relay server: the correct configuration syntax, three common pitfalls to avoid, and how to verify that it’s actually working. You can use this as a troubleshooting checklist and follow the instructions exactly.

<Callout emoji="🧭">
  One-line conclusion:
  <strong>
    <code>base_url</code> must be written inside the{' '}
    <code>[model_providers.xxx]</code> block, and then the top-level
    <code>model_provider</code> to point to
  </strong>
  . A <code>base_url</code> written directly at the top level will be completely
  ignored by the new version of the Codex.
</Callout>

## Conclusion First: The Correct config.toml

The configuration file is located at `~/.codex/config.toml` (`C:\Users\你\.codex\config.toml` on Windows). Here is the minimal configuration that works:

```toml
model = "gpt-5.6-sol"          # 换成中转站支持的模型名
model_reasoning_effort = "high"
model_provider = "qnvip"       # 指向下面的 provider 块
experimental_bearer_token = 'sk-xxxxxxxx'   # 中转站的 key，鉴权用

[model_providers.qnvip]
name = "qnvip"
base_url = "http://中转站域名/v1"
wire_api = "responses"         # 中转站不支持 responses 就改成 "chat"
```

Structurally, there are only three things that must align:

1. The value of the top-level `model_provider` is equal to the `xxx` in `[model_providers.xxx]`.
2. `base_url` is defined inside the `provider` block, not at the top level.
3. Authentication uses the top-level `experimental_bearer_token` and does not depend on environment variables.

## Three Common Pitfalls

### Pitfall 1: `base_url` Written directly at the top level → Completely ignored (main cause)

This is why the vast majority of people get stuck. The new version of Codex **does not recognize the top-level `base_url`**. If there is no `[model_providers.xxx]` block with `model_provider` pointing to it, it falls back to the built-in OpenAI provider, which is hard-coded to `api.openai.com`.

| Syntax                                                         | Result                                                                                                            |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| ❌ `base_url` Written directly at the top level                | Silently ignored with no error messages; the request is routed to `api.openai.com`, resulting in a 401 error      |
| ✅ `base_url` Written inside the `[model_providers.xxx]` block | Works in conjunction with `model_provider` at the top level; the request is correctly routed to the relay station |

Incorrect syntax (explicitly written at the top level; invalid):

```toml
base_url = "http://中转站域名/v1"   # ❌ 被忽略
wire_api = "responses"
```

### Pitfall 2: An extra quote at the end of the key

It’s very easy to make a mistake when copying and pasting a key. For example, `'sk-...4eb5"'` — the extra `"` at the end will be treated as part of the key, corrupting the entire key. As a result, even if the provider is paired, the relay station will report `invalid_api_key`.

<Callout emoji="✂️">
  Check that the quotation marks are <strong> in pairs and clean </strong>:
  Single quotes with single quotes, double quotes with double quotes; do not mix
  them. After pasting the key , move the cursor to the end of the line to
  confirm there are no extra characters.
</Callout>

### Pitfall 3: Custom provider doesn't read `auth.json`

In the Codex built into the ChatGPT desktop version, there is a `auth.json`, and the `OPENAI_API_KEY` within it is **intended only for the built-in OpenAI provider**. If a custom provider specifies `env_key = "OPENAI_API_KEY"`, it reads the actual system environment variables rather than `auth.json`, resulting in the following error:

```text
Missing environment variable: OPENAI_API_KEY
```

Two solutions; I recommend the first one:

- ✅ **Use the top-level `experimental_bearer_token`**: This doesn’t rely on environment variables, so it works reliably whether launched from the command line or via the desktop app.
- ⚠️ Or use `export OPENAI_API_KEY=sk-xxx`, and then write `env_key = "OPENAI_API_KEY"` in the provider. Note that when the desktop app launches, it **may not inherit** the exports from `~/.zshrc`, so it can be hit-or-miss.

## Verification Methods

It must be run in the **trusted directory**; otherwise, it will return the error `Not inside a trusted directory`:

```bash
cd /受信任的项目目录
echo "只回复两个字:成功" | codex exec --skip-git-repo-check
```

Check the startup message to see if "`provider:`" is the name of your relay station and whether it returns content normally. If you receive the word "Success," it means the entire connection is established.

## Quick Reference Table for Error Messages

Compile a table of common errors and their corresponding causes so you can quickly identify the issue when it arises:

| Error                                          | Cause                                                                       | Resolution                                                              |
| ---------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 401 and the URL is `api.openai.com`            | `base_url` Did not enter the provider block / provider not active           | Check if `model_provider` and `[model_providers.xxx]` match             |
| 401 `invalid_api_key` (URL is a relay server)  | Incorrect key / key contains extra characters                               | Recopy the key and ensure all quotation marks are properly paired       |
| `Missing environment variable: OPENAI_API_KEY` | `env_key` is used but environment variables are not set                     | Switch to `experimental_bearer_token`                                   |
| 404 / Incorrect path                           | `wire_api` is set to `responses`, but the relay server only supports "chat" | Change to `"chat"`; or check if `/v1` is missing or extra in `base_url` |
| `Not inside a trusted directory`               | Not in a trusted directory                                                  | Add `--skip-git-repo-check` or run it from a trusted directory          |
