# Blog GEO Redesign

First, let’s define what GEO is: **Generative Engine Optimization**.

SEO is about getting content to rank high in search results, while GEO is about getting content **cited in AI-generated answers**—when engines like ChatGPT, Claude, Perplexity, and Google AI Overviews provide answers directly, does your site get cited as a source, mentioned by name, or linked to?

This term comes from a 2023 paper (Aggarwal et al., later published in KDD).They conducted experiments to compare which rewriting techniques could improve the “citation rate,” and their conclusions were quite counterintuitive: **Including specific statistics, citing authoritative sources, and inserting direct quotes from experts resulted in a 30–40 percent improvement in performance, whereas traditional keyword stuffing had virtually no effect.**

<Callout emoji="🧭">
  Let’s start with a reality check: GEO and SEO overlap significantly at the
  core (authority, original content, citations from other sources). It’s not a
  new track replacing SEO; rather, it’s a reweighting of the same set of tasks
  in the era of zero-click search results. Many “GEO services” on the market are
  simply SEO sold under a different name.
</Callout>

This blog [underwent an SEO overhaul in the previous round](/blog/20260729-nextjs-i18n-seo-overhaul), and the foundation is solid. This time, I’m implementing GEO on top of that, and in the process, I uncovered two live issues—what they have in common is that **they look completely normal in the code.**

## Explore Online First, Then Read the Code

The first step isn't to make changes—it's to take stock of what you have. Use `curl` to check the sitemap, `robots.txt`, feeds, and a few specific URLs one by one.

The good news is that the foundation is indeed solid: article pages are server-rendered, and the full body text is included in the HTML (AI crawlers generally don’t run JavaScript, so many SPA blogs are eliminated at this stage); `robots.txt` is `User-Agent: *` / `Allow: /`, and GPTBot, ClaudeBot, PerplexityBot, and Google-Extended all pass;There are four JSON-LD blocks per page: `BlogPosting`, `Person`, `WebSite`, and `BreadcrumbList`, which are cross-referenced using `@id` to form a graph.

Here's the bad news:

## The favicon keeps returning a 500 error

It's not just the favicon. `/apple-touch-icon.png`, `/llms.txt`, and any URL in the root directory that contains a period and doesn't exist—they all return a 500 error.

The root cause is that two properly designed systems collided:

```ts title="middleware.ts"
export const config = {
  matcher: ['/((?!api|_next|_vercel|.*\\..*).*)'],
};
```

The middleware uses `.*\..*` to allow all paths containing dots (the intention being to avoid blocking static resources). Meanwhile, `app/[locale]` is the dynamic segment, which **matches any single-segment path**. As a result, `/favicon.ico` bypasses the middleware and is treated by the App Router as `locale = "favicon.ico"`, proceeding all the way to:

```tsx title="app/[locale]/layout.tsx"
const { locale } = await params;
const messages = (await import(`../../messages/${locale}.json`)).default;
```

`messages/favicon.ico.json` Does not exist → `MODULE_NOT_FOUND` → 500.

Repair is a line of defense:

```tsx
if (!isLocale(locale)) {
  notFound();
}
```

<Callout emoji="🔍">
  I was able to pinpoint this bug only after seeing the actual error message in
  the dev server logs. Just looking at the code, there’s nothing suspicious
  about the `[locale]` layout—it simply trusted the parameters provided by the
  router.
</Callout>

While I was at it, I copied `favicon.ico` to the root directory of `public/`, and that path now returns a 200 status code.

## Modification 1: A single paragraph in each article that can be extracted as a conclusion

This is the one with the highest return on investment.

Generative engines extract paragraphs that **stand on their own, independent of context**. However, such paragraphs typically do not exist in technical articles—conclusions are scattered across five subsections, so the model has to piece them together on its own.

So I added a frontmatter field named `tldr`, completing all 18 posts. It appears in three places:

- Visible block at the top of the main content
- schema.org for `BlogPosting` `abstract`
- Length validation for `check-seo` (display width of 30–200)

The component is intentionally kept very simple: a `<section>` containing `data-tldr`, with no nested tags between the label and the sentence, making it easy to extract the entire paragraph.

Interestingly, that length rule immediately flagged five of my own excessively long lines; I had to compress them before it passed.

## Modification 2: Pass the Q&A and steps directly to the engine

Three new schema.org builders have been added, with frontmatter opt-in:

| Type          | Coverage   | Content                                                                      |
| ------------- | ---------- | ---------------------------------------------------------------------------- |
| `FAQPage`     | 7 articles | 27 Q&A sets                                                                  |
| `HowTo`       | 4 articles | 18 steps; each step in the Traefik article includes verified section anchors |
| `DefinedTerm` | 3 articles | Obsidian, Harness Engineering, SDKMAN                                        |

After deduplicating, there are a total of 9 articles. All answers were extracted from the error correction tables and the main text of the articles; no new content was written.

<Callout emoji="⚠️">
  It’s important to note: Starting in 2023, Google will no longer display FAQ
  and How-To rich results for most sites, so **this section will not result in
  any changes to how your search results appear**. Its value lies in feeding
  question-answer pairs and step-by-step sequences directly to generative
  models, eliminating the need for the model to infer information from prose.
</Callout>

All three builders use defensive parsing; when the frontmatter is written incorrectly, they return "`null`" instead of causing the build to fail.

## Modification 3: 18 Automatically Generated Share Cards

None of the previous articles had cover images, so when they were shared, only the site's default banner appeared.

I had originally planned to use Next's `opengraph-image` file convention, but the build immediately returned an error:

```text
Error: Catch-all must be the last part of the URL.
```

The article route is a catch-all (`[...slug]`), and Next does not allow the image convention segment to follow it. Change it to a route handler (`app/og/[slug]/route.tsx`), and the URL is (`/og/<slug>.png`).

Here’s a tip to avoid a pitfall: **Don’t place it under `/api/`**, because `robots.ts` contains `Disallow: /api/`, and social media crawlers can’t access the images below that.

The real problem is the font. `next/og` The base font is Satori, **which doesn’t include any Chinese characters**; if you don’t explicitly pass the font along, Chinese titles will render as a block of garbled characters. The full Noto Sans SC font is 18 MB, so it’s not practical to include it in every image generation.

The solution is subset creation: fix the variable font to the two weights of 400 and 700, then trim it according to the character set.Character set = the entire site’s corpus + **the 3,755 characters in the GB2312 Level 1 character table** as a fallback—using only the existing corpus would result in just 1,143 characters, making it easy for new articles to exceed the character limit.

The final result consists of 3,988 characters, with two font weights, each 1.1 MB in size. These fonts are used only for rendering during the build process and are not sent to visitors.

There is one more reinforcement:

```ts
export const dynamic = 'force-static';
export const dynamicParams = false;
```

The font path is concatenated at runtime by `process.cwd()`. Next.js’s file tracking cannot detect this statically, so the TTF file is not included in the serverless function package. Therefore, unrendered slugs must return a 404 error at the routing layer, rather than failing after entering the handler function because the font cannot be found.

## Modification 4: RSS Outputs Full Text, Then Gets Stuck on Its Own Articles

Previously, the feed only included `description` (summary); subscribers had to click back to the site to read the full text.

The challenge is that the main content is written in MDX: there are 470 instances of `<div className>` and 22 instances of `<Callout>` across the 18 articles, as well as several custom components. `contentlayer` only exposes `body.raw` (MDX source code) and `body.code` (compiled bundle); there is no ready-made HTML.

I wrote a remark/rehype pipeline: strip out presentational JSX (the reader has no stylesheets or React, and the Tailwind wrapper is just noise), map things like `Callout` to semantic HTML, and then rescue the content hidden inside props—The code for `CopyableCodeBlock` and the error for `ErrorDisplay` are both inside the props; simply stripping them out would cause them to be silently lost.

Then an error occurred during XML parsing:

```text
xml.etree.ElementTree.ParseError: not well-formed (invalid token)
```

The number of CDATA tags is balanced, and the structure looks fine. After searching for a while, I found that the culprit is this line:

```js
width += /[⺀-￿]/.test(char) ? 2 : 1;
```

This is the regular expression used in `check-seo` to calculate the display width of Chinese characters, with an upper limit of **U+FFFF**. It appears in the feed because [that article on the previous round of SEO updates](/blog/20260729-nextjs-i18n-seo-overhaul) referenced this code snippet.

U+FFFF is an invalid character in XML 1.0; **neither CDATA nor numeric references can save it**—the specification does not allow it to appear at all.

<Callout emoji="🪤">
  This was a pitfall the author dug for themselves in that article: it cited
  code written during that very same round of revisions. If it hadn’t been for
  the full-text RSS project six months later, it would never have been
  discovered.
</Callout>

Processed into the escape sequence `\uXXXX`: This is both valid XML and, within the context of a code block, remains equivalent and readable JavaScript—a better solution than simply deleting it. This also addresses the C0 control character and the lone proxy entry.

The feed size increased from approximately 14 KB to 208 KB. Tag feeds remain in summary format—all 51 tag feeds are subsets of the same set of articles, and repeating the full text offers no benefit.

## Modification 5: llms.txt

Follow the [llmstxt.org](https://llmstxt.org) guidelines to output the site navigation at the root path; it is statically generated during build and its content automatically updates along with the articles.

The structure consists of an H1 heading, a one-sentence summary, and a paragraph of context, followed by a list of links organized into sections labeled `## Posts`, `## Pages`, and `## Optional`. For each article, **`tldr` is used directly as the description**—which is exactly what this field is for. A single crawl allows the model to capture the site-wide structure and the key points of each article.

Its adoption rate is limited; it falls into the category of low-cost measures that can be easily implemented—but don’t expect immediate results.

## Modification 6: Automatic Maintenance of `lastmod`

`lastmod` The field already exists, and both `sitemap.ts` and the structured data are reading it. What’s missing is the **value**: none of the 18 articles have had this value filled in, so `dateModified` keeps dropping back to `datePublished`, which effectively tells the engine that “these articles haven’t been updated since they were published.”

Since I’m bound to forget what I wrote by hand, I’ll deduce it from the Git history. Here’s a pitfall that isn’t immediately obvious:

The straightforward approach is to use `git log -1 --format=%cI -- <file>`. However, when the script writes `lastmod`, it creates a new commit, which becomes the latest change to that file. The next build reads the new date and writes it again—**the script feeds on its own output, causing the date to increment indefinitely**.

So, check the diffs for each commit to that file one by one, **skipping the commits that only changed the `lastmod:` line**, until you reach the commit that actually changed the content.

Another pitfall is Vercel: By default, it performs a shallow clone, and `git log` cannot retrieve the history of older files. When the script detects `--is-shallow-repository`, it skips it and uses the committed value—which is written and committed by the local build, while the build machine is only responsible for reading it.

## Embedding Rules into the Build Process

If I keep new agreements only in my head, I won’t even remember them six months later. So I’ve written them all down in `check-seo`:

- `tldr` Missing character warning + 30–200 display width
- Field shape validation for `faq` / `howto` / `definedTerm`
- OG card font character missing detection (if a character outside the subset is used in the title, an error is reported in advance rather than discovering a blank box only upon sharing)
- `lastmod` error reported before `date`

The value of this system lies in the fact that: **it turns the suggestion that “an article should have a concluding sentence” into a rule that causes the build to fail.**

## If You Want to Do GEO, Too

Based on the order of this round, it’s worth doing these things first:

1. **Check the site first, rather than reading the code.** Use `curl` to test each URL in the sitemap, as well as the `robots.txt` file and the favicon, one by one, to see the actual response codes. The two most valuable discoveries from this round came from doing just that.
2. **Make sure AI crawlers aren’t blocked.** Many sites have excellent SEO but end up blocking GPTBot altogether.
3. **Add a self-contained conclusion to every post.** It offers the highest return on investment at virtually no cost.
4. **Convert Q&A and step-by-step instructions into structured data.** Don’t count on rich media results; instead, focus on eliminating the need for model inference.
5. **Output the full text via RSS.**
6. **Incorporate new conventions into build checks.**

As for the content itself—the paper’s conclusion still holds true: specific figures, authoritative citations, and direct quotes are more effective than any keyword tricks. In this regard, GEO’s standards align with those of well-written articles.

## A Conclusion That Hasn't Changed

At the end of my previous article on SEO optimization, I wrote, “Use curl to test each URL in the sitemap one by one.”

This round confirmed it once again, and even more thoroughly: the 500 error with the favicon isn't visible in the code, nor are the invalid characters in the feed—the latter was even caused by the code cited in that article itself.

**Just because the code reads fine doesn't mean it will work in production.** I'll probably have to keep writing this for a few more years.
